# Data Folder — Design Principles

This folder holds the **data layer** for AltArmy TBC: persistence, aggregation, and list/view logic. UI (tabs) and other features consume this layer; they do not read SavedVariables or WoW APIs directly for character data.

---

## Folder layout

Modules are grouped by domain. Filenames and `AltArmy.*` namespaces are unchanged; only disk paths differ.

| Folder | Contents |
|--------|----------|
| **(root)** | Shared utilities: `CharKey`, `ClassColor`, `Debug`, `MailAlerts`; docs (`DESIGN.md`, `DATA_VERSIONS.md`) |
| **DataStore/** | Persistence core + scan modules: character, containers, equipment, currencies, professions, reputations, mail, auctions, talents, lockouts, level history; `LevelProgressData` |
| **Characters/** | Summary list/view, realm filters, bank-alt flags/detect, net worth |
| **Gear/** | Item stats/usability, gear score, compare/upgrade, Pawn scales, upgrade alerts |
| **Search/** | Search settings, index, query, present, engine, guild nav, recipe yield bonus |
| **Guild/** | Guild share settings/protocol/data/comm, tab helpers, chat main-name, manual groups, note parser |
| **Cooldowns/** | Cooldown data/alerts, lockout list helpers, stockpile mail plan |
| **Recipes/** | Generated per-client recipe tables (`RecipeData_TBC`, `RecipeData_Forever`) and their reader (`RecipeInfo`); see [Recipe data](#recipe-data) |
| **Integrations/** | Optional addon bridges (RestedXP, Zygor) |
| **Auctions/** | Auction house scans, full or summary (`AuctionScan`), and the order book (`AuctionBook`: encode, decode, latest scan, summaries) |
| **Economy/** | WoW Forever's Waylaid Crates and bundles (`WaylaidCrates`, generated by `scripts/generate-waylaid-crates.py`) and their fill costs over the order book (`WaylaidCosts`, pure); the Currency grid's rows and sorting (`CurrencyGrid`, pure) |

## DataStore: Core + Modules

**DataStore** is split into a **core** file and **domain modules**. The single public API remains `AltArmy.DataStore`; consumers (SummaryData, Characters, Tabs) call `DS:GetRealms()`, `DS:GetCharacter(name, realm)`, `DS:GetProfessions(char)`, etc. unchanged.

- **DataStore.lua (core)** — Namespace, SavedVariables (`AltArmyTBC_Data`), `GetCurrentCharTable` / `GetCurrentCharacter`, `DATA_VERSIONS`, `MigrateDataVersions`, and the single event frame. Registers all WoW events and dispatches to module methods (e.g. `DS:ScanCharacter()`, `DS:ScanBags()`). Exposes shared data to modules via `DS._GetCurrentCharTable` and `DS._DATA_VERSIONS`. Cross-cutting APIs: `GetRealms`, `GetCharacters`, `GetCharacter`, `GetCurrentCharacter`, `HasModuleData`, `GetDataVersion`, `NeedsRescan`, `GetAllDataVersions`.
- **Module files** — DataStoreCharacter, DataStoreContainers, DataStoreEquipment, DataStoreCurrencies, DataStoreProfessions, DataStoreReputations, DataStoreMail, DataStoreAuctions, DataStoreTalents, DataStoreLockouts, DataStoreLevelHistory. Each attaches its scan function(s) and getters to `AltArmy.DataStore`. Load order: core first, then modules; DataStoreCurrencies loads after DataStoreContainers (ScanCurrencies uses GetContainerItemCount). DataStoreCurrencies also scans the native currency list (`ScanCurrencyList`, debounced on `CURRENCY_DISPLAY_UPDATE`) into `char.CurrencyList` and account-wide `AltArmyTBC_Data.CurrencyMeta`; listeners registered with `DS:OnCurrencyListChanged` run after each scan. **OwnRecipeRead** (`AltArmy.OwnRecipeRead`, loads right after DataStoreProfessions; WoW Forever only) is not a scan of its own: it opens the player's own professions out of sight through a profession link, so DataStoreProfessions' recipe scan runs without the player opening any window (see "Learned recipes" below).

Guild share payloads use separate SavedVariables (`AltArmyTBC_GuildData`, `AltArmyTBC_SharingSettings`) owned by the Guild modules, not `AltArmyTBC_Data.Characters`.

The auction house's order book for altarmy-profit has its own SavedVariable too (`AltArmyTBC_AuctionBook`), owned by `Auctions/AuctionBook.lua` (pure: ladders, encoding, pruning) and written by `Auctions/AuctionScan.lua` (the client's full scan, read a batch a frame). Full scans go in `scans`, which altarmy-profit reads. Summary scans (the client's browse results: one row per item, cheapest unit price and units listed) go in a separate `summaries` list, one per realm and faction, so they never displace a full scan and are never uploaded as one; altarmy-profit's parser ignores the key. Additive, so the book's `version` stays 1. It is not character data and does not go through DataStore.

See [DATA_VERSIONS.md](DATA_VERSIONS.md) for per-module format versions.

## Layering

Data flows in one direction:

1. **DataStore (core + modules)** — Persistence and scanning  
   - Core owns `AltArmyTBC_Data` (SavedVariables) and the event frame; modules attach scans and getters.  
   - Scans the current character on WoW events (e.g. `PLAYER_ENTERING_WORLD`, `PLAYER_MONEY`, `TIME_PLAYED_MSG`).  
   - Exposes: `GetRealms()`, `GetCharacters(realm)`, `GetCharacter(name, realm)`, `GetCurrentCharacter()`, and per-field getters on character data (and containers, equipment, professions, etc.). `GetCharacter` and `DeleteCharacter` accept a character name or a storage key. `GetCharacters` and `ForEachCharacter` hand out storage keys, so callers read the name from `charData.name`.

2. **SummaryData.lua** — Aggregation and formatting  
   - Reads from DataStore only (no direct SavedVariables access).  
   - Builds a flat list of character entries for the Summary tab.  
   - Entry shape: `name`, `realm`, `level`, `restXp`, `wellRestedRank`, `money`, `played`, `lastOnline` (raw values: copper, seconds, timestamps).  
   - Provides display helpers: `GetMoneyString`, `GetTimeString`, `FormatLastOnline`, `FormatRestXp`, `PresentWellRestedTooltip`.  
   - Aggregates missing-data warnings via `GetMissingDataInfo`.

3. **Characters.lua** — List and view  
   - Gets list via `SummaryData.GetCharacterList()`.  
   - Maintains a cached list and a view (indices); supports sorting.  
   - Exposes: `InvalidateView()`, `GetView()`, `GetList()`, `Sort(ascending, sortKey)`.  
   - Tabs (e.g. TabSummary) use Characters for the scroll list; they do not call SummaryData or DataStore directly for that list.

**Rule:** Each layer talks only to the layer below. Tabs talk to Characters (or SummaryData only for formatting); they do not talk to DataStore for list data. Other domains (Search, Gear, Guild, Cooldowns) have their own helpers above DataStore.

---

## Single Source of Truth

- **DataStore** is the only writer to `AltArmyTBC_Data`. All character data comes from WoW APIs + events and is written in DataStore.
- **SummaryData** is stateless for the list: each `GetCharacterList()` call builds the list from DataStore. No local cache of the full list.
- **Characters** caches the list and view. When underlying data may have changed (e.g. after login, tab show), the UI calls `Characters:InvalidateView()` so the next `GetView()`/`GetList()` rebuilds from SummaryData.

---

## Raw Values vs Display

- **Stored and passed:** Raw values (copper, seconds since epoch, seconds played). This keeps sorting and logic simple and locale-independent.
- **Display:** Formatting (e.g. "5g 20s", "2d 3h ago", "50%") lives in SummaryData helpers or in the UI (TabSummary column `GetText`). The data layer does not store formatted strings for these fields.

---

## TBC Compatibility

- No required external addon dependencies. DataStore is internal; no DataStore_Characters or similar.
- OptionalDeps (Auctionator, TacoTip, etc.) enrich features when present. Recipe metadata ships with the addon (see [Recipe data](#recipe-data)); CraftLib is no longer used.
- WoW API usage is defensive: check for function existence (e.g. `UnitName and UnitName("player")`, `GetRealmName and GetRealmName()`) so the addon runs on TBC Classic even when some APIs differ or are missing.
- SavedVariables key is `AltArmyTBC_Data`; structure is `Characters[realm][guid] = charData`, keyed by `UnitGUID("player")` so a renamed character keeps its data. Entries saved before GUIDs stay under their name until that character logs in again. `charData.name` is the full name: on WoW Forever `UnitName` returns the first name and surname as two values, which DataStore joins ("Frell Ofelements"). It is never `Unknown`. See `DATA_VERSIONS.md`, character v3.
- Profession cooldowns (`charData.ProfCooldownExpiry[spellId] = { expiresAtUnix }`): TBC fills them from `GetTradeSkillCooldown` / `GetCraftCooldown` when a profession window opens and from `GetSpellCooldown` after a tracked cast. WoW Forever has neither tradeskill function, so there the `C_TradeSkillUI` recipe scan reads `C_TradeSkillUI.GetRecipeCooldown` for tracked recipes, and the after-cast scan falls back to `C_Spell.GetSpellCooldown`. The saved shape is the same on both clients. The login profession scan (`ScanProfessionLinks`) removes professions it no longer sees, but it skips `DS.PROFESSIONS_OUTSIDE_SKILL_SCAN` (Comprehension). Forever's `GetProfessions()` has no slot for Comprehension, so only its recipe scan ever adds it.
- Per-character settings (Summary/Gear/Reputation pin and hide, Graph selection, bank alts, guild-share main and opt-outs) stay keyed by `AltArmy.CharKey(name, realm)`. When a character's stored name changes, `AltArmy.RekeyCharSettings` moves them to the new name.

## Recipe data

Search, the Guild tab and the learn flow need facts about every recipe the client has, not only the ones a character scanned: profession, crafted item, required skill, difficulty bands, and how it is learned. They come from two generated Lua tables in `Recipes/`, one per client:

- `RecipeData_TBC.lua` (TBC Anniversary) and `RecipeData_Forever.lua` (WoW Forever). Each returns at load unless it is on its own client (interface 16001 is Forever), so only one is ever in memory. It sets `AltArmy.RecipeData = { build, client, recipes }`, with `recipes[spellID] = { profession, resultItemID, reqSkill, yellow, gray, source, recipeItemID }` (false = unknown). Keys are recipe spell ids, the same ids `char.Professions[name].Recipes` uses.
- `RecipeInfo.lua` (`AltArmy.RecipeInfo`) is the only reader: `GetRecipe`, `GetDifficulty` (orange below yellow, green from the floored midpoint of yellow and gray, gray at gray), `EnrichEntry` (Search/Guild rows: `recipeSkillRequired`, `difficulty`, `recipeSource`, missing `resultItemID`), `SourceIncludes`, `FindRecipeLearnInfo`, and the skill-cell formatters. Names come from `GetSpellInfo` (or `C_Spell` on Forever) at run time, so the tables carry no localized text.
- `source` lists every way to learn a recipe, `|`-joined in this order: `starter` (learned with the profession), `trainer`, `quest`, `vendor`, `reputation`, `drop`. The Search source filter keeps a recipe when any of its sources is enabled.

**Learned recipes.** When a recipe is learned with its profession window closed (`NEW_RECIPE_LEARNED` id, or the learn line in system chat), `DS:OnRecipeLearnDetected` asks `FindRecipeLearnInfo` which recipe it was (by id, crafted item, or the client's recipe name; a name two professions share goes to the one the character has) and stores it with its difficulty color, so it shows in Search and guild share without reopening the window. Only a recipe it can't identify or store marks professions stale for the Summary warning.

**Recipes read in the background (WoW Forever).** `OwnRecipeRead.lua` reads only stale professions: those marked in `professionsNeedingRecipeScan` or with no recipes stored. Each read opens the profession window, which plays its sound, so a profession whose recipes are already stored is never read. It reads 10 s after login or a reload (`PLAYER_ENTERING_WORLD`), in the game's order, and 3 s after `OnRecipeLearnDetected` marks a profession stale (every stale profession when it can't tell which). How a read works:
- It sets a hidden tooltip's hyperlink to `trade:<player GUID>:<profession spell>:<skill line>`. That needs no click, unlike `C_TradeSkillUI.OpenTradeSkill`. The spell comes from `GetProfessionInfo`'s spellbook offset, and its other spells are tried in turn when one gets no answer within 3 s; the spell that worked is remembered for the session.
- The client then opens the profession, and the usual `TRADE_SKILL_SHOW` / `TRADE_SKILL_DATA_SOURCE_CHANGED` scan stores it. `DS:ScanRecipes` then calls `R.OnRecipesScanned`, which closes the window.
- Reads run one at a time, 1 s apart. They wait while the player is in combat, typing or has a panel open, and stop on entering combat and logging out.
- While a read runs, Blizzard's own `TRADE_SKILL_SHOW` handlers (UIParent's, ProfessionsFrame's) are unregistered so the window never shows. Should it open anyway, `ProfessionsFrame` is hidden (alpha 0, tiny scale, no mouse). Other addons' handlers and the DataStore frame are left alone.
- `AltArmyTBC_Options.autoReadRecipes == false` turns it off (Options > General > Advanced).

`ScanRecipesViaTradeSkillUI` stores only the character's own window: it skips guild and NPC crafting windows and other players' linked professions. A linked window under the player's own name, or naming nobody during a read, still counts as their own. Only professions on `R.LINKABLE_SKILL_LINES` are read: the server answers links only for skill lines DB2 marks `CanLink` (not Fishing, Mining, Herbalism, Skinning or Comprehension; `R.CanRead` by name, for alts). With background reads, the Summary warning about missing recipes in a profession that can be read tells an alt only to log in.

**Generating.** `scripts/generate-recipe-data.py --version tbc|forever` builds a table from the client's DB2 tables (wago.tools CSV exports, cached in the monorepo's `.cache/wago/<build>/` by the site's `gamedata.py`, which the script loads by its path) and the server facts in `data/recipes/<version>/`. It is made at the build pinned in the monorepo's `site/data/game-data.json`, the same build the site loads, and names it in the file (`local BUILD`; the site's tests check the two agree); `--build latest` uses wago's newest build instead, `--check` verifies the file. The DB2 tables give the recipes, professions, crafted items, difficulty bands, recipe items and their faction requirements. What only the server knows (trainer skill requirements, quest-taught spells, where recipe items come from) is read from the open-source emulators' world databases by `scripts/build-recipe-server-facts.py` into committed CSVs: cmangos' tbc-db for TBC, vmangos (vanilla 1.12) for Forever. By default it reads the release pinned in `game-data.json` from the monorepo's `.cache/emulators/`, downloading it while it is still the emulator's newest (`--cmangos`/`--vmangos` take a file). `data/recipes/<version>/overrides.csv` is applied last: hand-checked required skills and sources for recipes the server data lacks or gets wrong (each row notes what it replaced).

**Watching for new data.** The monorepo's `game_data.py` and its daily `.github/workflows/game-data.yml` keep this and the site's game data on one pin. Each day it regenerates everything made from the game data at wago's newest builds and the emulators' newest releases (the server facts, both tables, `Economy/WaylaidCrates.lua`, and the site's vendor, recipe source and city files), runs the site's and the addon's checks, and commits any change to main with the pins moved (a PR instead when a build's major.minor.patch moved: the interface and CurseForge versions then need a person). It then releases the addon (`release.py addon --patch`) when only generated data changed in `AltArmy_TBC/` since the newest `addon-v*` tag; with hand-written work waiting, the next manual release ships it. An override whose spell is gone fails the run. No step needs a local run; `game_data.py update --to pinned` on a clean checkout must change nothing.

**Checked against CraftLib (TBC, 2026-10-02).** The TBC table holds all 2,112 CraftLib recipes, plus 79 CraftLib doesn't list (25 Poisons; the rest mostly old or unused spells), and every recipe scanned on the developer's account resolves to its profession. After the overrides, the differences left are accepted:

- Result item: CraftLib names a reagent (e.g. Strange Dust) as the "item" an enchant makes; the table has none (0), as the client does.
- Source: 28 recipes learned with the profession are `starter` here, `trainer` in CraftLib; 4 taught by a quest (Mooncloth Boots, Restorative Potion, Smoked Desert Dumplings, Tranquil Mechanical Yeti) are `quest` here, `trainer` in CraftLib. Recipes with several sources list all of them; CraftLib picks one.
- Difficulty bands come from the client and win where CraftLib differs by a few points (Goblin Jumper Cables, Runed Eternium Rod, Nexus Transformation). The Mortar: Reloaded has placeholder bands (1/1) in the client, so it shows no difficulty.
- Alchemist's Stone requires 350, as its recipe item does (CraftLib: 300).

Forever has no CraftLib data to check against, and vmangos is vanilla data: Forever-only recipes can have no required skill or source until overrides fill them in.

## Extensibility

- **DataStore:** New character fields or domains can be added in a new module file (or existing module); the module attaches its scan and getters to `AltArmy.DataStore`. Core’s event handler is extended to call the new scan when appropriate. Bump `DATA_VERSIONS` and document in `DATA_VERSIONS.md`.
- **SummaryData:** New entry fields can be added to the table returned by `GetCharacterList()`; new formatting helpers can be added alongside existing ones.
- **Characters:** `Sort()` can be extended to support new sort keys; the view/list model stays index-based so UI code does not need to change for new columns.

## Conditional / situational stats (Gear)

Some items only grant part of their bonus under a condition (zone type, form, etc.), e.g. "Equip:
Increases all Resistances by 3. Gain an additional 5 to all Resistances in Forest and Grassland
areas." A normalized stats table from `ItemStats.GetNormalized(link)` (`Data/Gear/ItemStats.lua`)
stays a flat `shortKey -> number` map for always-on stats; conditional stats live under a single
reserved key, `stats.conditional`, mapping the condition's tooltip text to a nested table of the
same shape:

```lua
{
    fire_res = 3, -- always-on
    conditional = {
        ["in Forest and Grassland areas"] = { fire_res = 5, --[[ ... ]] },
    },
}
```

`GearCompare.lua`'s row builders pull `stats.conditional` out before doing arithmetic over the
rest and render each conditional sub-stat as its own row, excluded from the weighted score.
New wordings are added as rows in `ItemStats.lua`'s `CONDITIONAL_STAT_PATTERNS` table (and, for a
genuinely new stat, one `IS.STAT_ALIASES`/`IS.STAT_LABELS` pair) — see the comments above that
table for the pattern shape.

## Namespace

Modules live under the `AltArmy` global. Common entry points:

- `AltArmy.DataStore` — DataStore API  
- `AltArmy.SummaryData` — SummaryData API and formatting  
- `AltArmy.Characters` — Characters list/view API  
- `AltArmy.BankAlt` / `BankAltDetect` — bank-alt flag  
- `AltArmy.SearchEngine` / `SearchSettings` / … — search  
- `AltArmy.GearUpgrade` / `GearCompare` / `GearScore` — gear  
- `AltArmy.CooldownData` / `LockoutData` / `StockpilePlan` — cooldowns  
- `AltArmy.GuildShareSettings` / `GuildShareComm` / … — guild share  
- `AltArmy.LevelProgressData` — graphs data
- `AltArmy.DataStoreLegacy` — WoW Forever Legacy Talent capture (speculative `C_Traits` API — see `docs/WOW_FOREVER_COMPATIBILITY_RESEARCH.md`)  

The Data folder does not introduce new globals beyond the `AltArmy` namespace tree.
