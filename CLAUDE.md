# CLAUDE.md

Conventions for AI agents working in this repository.

## Project

`altarmy-profit` is a website (a Python API and a React front end) that finds profitable crafting recipes and production chains for **World of Warcraft: Forever**. Items and recipes come from client DB2 tables (wago.tools CSV exports) loaded into the database (Postgres on the site, SQLite in development and tests); auction house prices come from the full scans players take with the Alt Army addon and upload; the engine ranks recipes by profit (buy or craft reagents, then sell via vendor, AH minus the 5% cut, or disenchant). See `README.md` for usage and roadmap.

## Layout

- `src/altarmy_profit/versions.py` – the game versions (`tbc` TBC Anniversary, `forever` WoW: Forever): each `GameVersion` names its `data/<version>/` data files, wago.tools product and pinned build, interface number, WoW flavor folder (`_anniversary_`, `_classic_beta_`), level and skill caps (`max_level`, `max_skill`), AH cut and postage, whether its prices are first-party (`first_party_prices`, Forever: from Alt Army's scans and hand-set prices alone), and what reputation takes off at vendors (`reputation_discounts`: (standing, percent) pairs; Forever 10% from Honored)
- `src/altarmy_profit/db.py` – `Database(url)`: the engine factory (SQLite or Postgres via SQLAlchemy Core), migrated to the newest Alembic revision and `game_versions` registered on first use; `default_url()` (`DATABASE_URL`, else `data/altarmy-profit.sqlite`); `Database(url, migrate=False)` never migrates (hosted instances: the deploy's migrate job does, and `upgrade` holds a Postgres advisory lock); pool sizes from `DB_POOL_SIZE`/`DB_MAX_OVERFLOW`; `upsert` (dialect-specific ON CONFLICT), build and row-count helpers (settings live in `users.py`)
- `src/altarmy_profit/schema.py` – every table as a Core `Table` on one `MetaData`; `src/altarmy_profit/migrations/` – Alembic env and revisions (`alembic.ini` at the root for the CLI); `tests/test_migrations.py` checks they match `schema.metadata`
- `src/altarmy_profit/auth.py` – `User(uid, tier, admin)`, `user_from_claims` (tier `free` iff the Firebase `sign_in_provider` is `anonymous`; `admin` iff a linked token carries the custom claim `admin: true`), `FirebaseConfig.from_env` (ValueError without `FIREBASE_PROJECT_ID`), the `TokenVerifier`, `AccountAdmin` and `AdminRoster` protocols and `FirebaseVerifier` (firebase-admin, in the `ui` extra; verifies tokens, deletes users, grants/revokes/lists the admin claim (`set_admin`, `admins`); honours `FIREBASE_AUTH_EMULATOR_HOST`)
- `src/altarmy_profit/users.py` – `ensure_user` (row on first sight, follows tier changes, sets `linked_at`), `delete_user` (cascades; nulls `price_snapshots.uploader_uid`), typed `UserSettings` (selection, `data_version`, time settings) per (user, game version); `trust`/`adjust_trust` (`users.trust_score`: halved per quarantined scan, +0.1 per accepted screened one)
- `src/altarmy_profit/uploads.py` – uploaded addon files: `ingest` (Alt Army replaces the uploader's characters via `service.replace_characters` and, where prices are first-party, records the auction house scans the file carries, `_record_books`: each for the house of the realm and faction the scan names, at the scan's own time, oldest first; a scan already recorded or older than the house's newest is passed over and left out of `Imported.realms`, since the file holds the last few scans and is sent again whenever it changes; an Auctionator file is refused there, `FIRST_PARTY_ONLY`. Elsewhere (TBC) Auctionator records every realm with prices, each key resolved alias first, then the uploader's matching character group, then parsed), `scan_time` (a time clamped to 30 days back and never the future), `decompress` (gzip, `MAX_BYTES` 32 MB), `record_upload`/`recent` history, `check_rate` (`RATE_LIMIT` 60/hour); every scan is screened with the uploader's trust (`RealmPrices.quarantined`, "not used" in the detail; the upload stays `accepted`)
- `src/altarmy_profit/watch.py` – the CLI watcher (`altarmy-profit watch`, no database): `find_files` (both versions, Alt Army first; `version_of` by flavor folder; no Auctionator file where prices are first-party), `changed` against a JSON state of mtimes, gzipped multipart over urllib (`Transport` injectable), `sync_once`, `run` (backoff; stops on `signin.SignedOut`); uploads send an `Auth` (a callable giving an ID token: `signin.Credentials`); standard library only (the WoW folder finders live in `wowfiles.py`, re-exported by `prices`)
- `src/altarmy_profit/book.py` – pure, standard library only: the auction house's order book from the Alt Army addon's full scans (`AltArmyTBC_AuctionBook`, its own SavedVariable in `AltArmy_TBC.lua`, written by the addon's `Data/Auctions/AuctionScan.lua` and `AuctionBook.lua`: per scan `{t, realm, faction, complete, listings, bidOnly, source, items}`, `items` being `<itemID>:<unit price>*<units>*<listings>,...;...`, at most 12 levels per item then a `~` tail). `read` (complete scans oldest first, read with `luasv.parse_assignment`; malformed is a ValueError), `Level`/`Ladder`, `encode`/`decode` (how a ladder is stored, with each level's `age`), `cost` (what `qty` units cost bought cheapest first, and the units short), `market_price` (the unit price 15% into the listed units), `aged`, `sold_between` (units gone at or under the cheapest price still listed were bought, those gone from behind it cancelled). `tests/fixtures/auction_book_v1.lua` is a copy of the addon's golden `spec/fixtures/auction_book_v1.lua`, so change both together
- `src/altarmy_profit/signin.py` – the watcher's and Alt Army Sync's email sign-in, standard library only: `fetch_config` (the site's `/api/config`), `sign_in`/`sign_up`/`refresh` against Firebase Auth's REST API (or the emulator the config names; every request sends the site as its Referer, since the browser key only answers the site's origins), `Credentials` (a refresh token that hands out ID tokens, refreshing 5 min early; `on_change` when Firebase rotates it), `SignInError` (readable reasons), `SignedOut`, `Unreachable`; `load_saved`/`save` keep only the refresh token per site (`~/.altarmy-profit/watch-auth.json`), never the password. There are no API keys: the `api_keys` table is unused and dropped with `local_sync` in the next revision
- `src/altarmy_profit/paste.py` – pure decoder of the Alt Army addon's export string (`AAX1:` + LibDeflate's printable encoding of raw DEFLATE of `V|`/`C|`/`P|`/`T|`/`R|` lines (`T|<spell id>|<rank>`: a Legacy talent; `R|<faction id>|<standing>`: a standing with a city faction, other factions' lines passed over, none from older addons); `decode`, `Export.game_version` from the client's interface). Format v2's `C|` line ends with the character's GUID (`Character.guid`, "" for characters saved before the addon stored GUIDs; not stored in the database); v1, from older addons, has none and is still read, but a v1 name that is a GUID (addon 2.1.3's export wrote its storage key) is a ValueError asking for a newer addon. The addon's `AltArmy_TBC/Data/ProfitExport.lua` (repo `../altarmy_tbc`) writes it; `tests/fixtures/altarmy_export_v2.txt` is a copy of the addon's golden `spec/fixtures/profit_export_v2.txt`, so change both together (`altarmy_export_v1.txt` keeps v1 covered)
- `src/altarmy_profit/tray.py`, `tray_core.py` – Alt Army Sync, the Windows uploader (`altarmy-sync`; the `tray` extra: pystray, Pillow): the watcher in a thread, a sign-in dialog (tkinter: sign in or create an account; `tray_core.form_problem` checks it), Start with Windows (HKCU Run), one instance per user; `tray_core` is its pure, tested part (`Target`: the live site by default, `--staging` or `--server URL` another, each with its own settings file, log, mutex and Run entry; `~/.altarmy-profit/sync.json`: email, refresh token, the release last announced; status line, autostart command with the target's flags; `check_for_update`: the newest `sync-v*` GitHub release if newer than `VERSION`, which `build_sync.py --version` stamps into the exe, "dev" from source and never checked; the tray asks every 6 h, notifies once and adds Update available to its menu). `scripts/build_sync.py` (the `build-tray` extra) makes `dist/altarmy-sync.exe`; `.github/workflows/sync.yml` publishes it as a GitHub Release on a `sync-v*` tag, and the Manage page links the latest
- `src/altarmy_profit/ingest.py` – download DB2 CSVs (`TABLES`, plus `OPTIONAL_TABLES` a client may lack: a 4xx is cached as an empty file and reads as no rows) and load one version's game data into the database; `output_count` reads either client's SpellEffect encoding; `fingerprint` hashes the ingest code (`FINGERPRINTED_MODULES`) and the version's hand-maintained CSVs, stored as `game_versions.ingest_fingerprint` (revision 0020) by every load, so the ingest job reloads a loaded build when either changed; `item_tooltips` computes every item's tooltip numbers and lines (`game_tables`, `item_spec` into `itemstats`)
- `src/altarmy_profit/itemstats.py` – pure item tooltip formulas: stat values from ItemSparse's allocations x RandPropPoints, armor (ItemArmorTotal x ItemArmorQuality x ArmorLocation, shields, bonus armor), weapon damage (the ItemDamage* tables), rendered as the white stat lines and green Equip lines (`STAT_NAMES`, `EQUIP_TEXT`, `RATINGS`: level-60 divisors hard-coded, since GameTables are not served; other level caps show ratings raw)
- `src/altarmy_profit/spelltext.py` – pure renderer of item spell effects (the Use / Equip / Chance on hit lines): `expand` fills a Spell description's `$` variables (`$s1`, `$o1`, `$d`, `$@spelldesc`, `${...}` arithmetic, `$?` conditionals take the else branch, unknown tokens stay as written) from a `SpellData` that ingest's `spell_data` builds for the item spells and what they reference; `render_effect` adds the cooldown to Use lines. `ingest.item_effects` reads Forever's ItemXItemEffect link or TBC's `ParentItemID`. `scripts/spotcheck_tooltips.py` compares computed lines with Wowhead's Classic tooltips (network, dev only)
- `src/altarmy_profit/engine.py` – pure profit/chain logic (no I/O). Every tree `Node` lists its `options` (vendor, ah, `craft:<recipe id>`, cheapest first) and the `option` taken; `Result.sell_options` gives each exit's best profit. `evaluate(recipe, choices)` takes user picks keyed by tree path (`r.0`, `r.0.1`; `sell` for the exit); subtrees with a pick skip the memo. With a `TimeModel(config, city)` (`Market(time=)`), nodes, options, steps and results carry seconds (all `compare=False`), options and exits are ranked by copper plus `time_value` x estimated seconds (`Market._effective`; a time value of 0 changes no plan), and `Result.timing` (lazy, like `steps`: `rank()` never times) routes the plan through the city (`time_result`); `Result.rate` is copper per hour. The model's city also prices vendor buys by the buyer's reputation (`Market(reputation_discounts=)`, `Crafter.reputations`, `vendor_price`, `Node.rep_discount`; `vendor_holders`, `cost_in`, `city_prices`, `recipes_using`: see Reputation discounts below). An item in `Market(books=)` is bought up its ladder (`_ah_cost`, `book.cost`), so its cost depends on the quantity; units the book is short of cost its dearest price (`Node.short`, `Result.short`); a plan's branches buying the same item share the ladder (`_share_books`, after the plan is chosen); an item with neither a book nor a price has no AH option
- `src/altarmy_profit/prices.py` – the price store and its sources: auction houses (`find_auction_house`, `auctionator_auction_house`, `unnamed_auction_house`), `record_book` (an Alt Army scan: every item's ladder into `price_current`, levels aged, items it no longer has unlisted, observations only for news, inferred sales into `price_sales_daily` when the scan before is at most `SALES_GAP` old; a scan no newer than the house's newest is `stale`; returns `BookRecorded`), `load_books` (what plans buy from: without levels first seen in the newest scan under `STRAY` of the 7-day median), `book_sell_price`, `record_snapshot` (every other source; writes observations only for news and moves `price_current`; a newer quantity alone updates `price_current.quantity` in place), `record_daily` (pools uploaders' days: min low, max high, max available), `prune`, `load_current`, `load_buy_and_sell` (the engine's buy and sell prices; `first_party=` reads only `FIRST_PARTY` sources), `load_listings` (`Listing`: cheapest listing, quantity, ladder and sale rate; `thin_market`, `THIN_UNITS`), `auction_houses` (with price counts), `coverage`, `stats`, `daily`; `screen`/`baseline` (quarantine), `record_auctionator(..., trust=)` and `record_screened` return `Recorded`; `record_daily_observations`; `set_price` (a manual price)
- `src/altarmy_profit/jobs.py` – runs of the scheduled CLI jobs in `job_runs` (revision 0010): `recording(database, job, game_version)` wraps a job (a row at start, then ok/failed and what it said via `Run.say`, each in its own transaction; `Run.warn` says it as a JSON line Cloud Logging reads as a WARNING with an `alert` tag; `sys.exit` with a message or non-zero code is a failure; runs unrecorded before the table exists), `recent`, `latest`, `late` (older than 2x `CADENCE`, which mirrors `deploy/setup.sh scheduler` and names the scheduled jobs; `schema.JOBS` still allows the removed ahledger job's old runs), `running` (unfinished and younger than `TIMEOUT`, the jobs' 30 min task timeout)
- `src/altarmy_profit/launch.py` – starting a job on demand (the Admin page's Run now): `run_ingest` (the ingest job's `--only-if-new` work, recorded; the CLI calls it too), `Launcher` protocol, `CloudRunJobs` (hosted: POSTs the Cloud Run Admin API's `jobs/<JOB_PREFIX>-ingest-<version>:run` with the service account's credentials (google-auth, via firebase-admin); `deploy.sh` sets `CLOUD_RUN_LOCATION` and `JOB_PREFIX` on the service, `deploy/setup.sh job-runner ENV` grants it `roles/run.invoker` on the ingest jobs), `InProcessJobs` (development: a thread of the API, one at a time), `from_env` (Cloud Run when both are set, else in-process on SQLite, else none: a hosted service never runs a job's work itself)
- `src/altarmy_profit/merge.py` – the merge (`altarmy-profit merge`, hourly Cloud Run job): `price_daily.median` and `price_current`'s 7-day columns (a scan's sample is its market price, else the minimum buyout), `sale_price` and `sale_rate` from the last 7 days of `price_sales_daily` (`MIN_SALES`), bumping `auction_houses.price_version` when anything moved; once `price_observations` reaches `PARTITION_AT` rows (5M) the CLI's merge logs a `Run.warn` tagged `PARTITION_ALERT`, which the log-based alert policy from `deploy/setup.sh alerts EMAIL` emails at most once a day
- `src/altarmy_profit/signals.py` – price signals through Firestore: `priceSignals/<auction house id>` holds only `{version, game_version, updated_at}` (the house's `price_version`, never prices); `Signals` protocol, `FirestoreSignals` (firebase-admin, lazy client, the `altarmy-<project>` app; `FIRESTORE_EMULATOR_HOST` in development), `NoSignals`, `for_project`/`from_env` (none without a project or with `PRICE_SIGNALS=off`), `publish_all` (logs failures, never raises). Published only after the transaction that bumped the version committed: `POST /api/uploads` (a background task) and the `merge` job. `firestore.rules`: signed-in users read `priceSignals`, nobody writes from a browser
- `src/altarmy_profit/auctionator.py` – pure parser for Auctionator's SavedVariables (TBC's prices; Forever's come from `book.py`) (Lua string holding CBOR): per item an `ItemPrice` (latest minimum buyout, per-day `DayStats` high/low/available)
- `src/altarmy_profit/timing.py` – pure play-time model (no engine import; the engine imports it): `TimeConfig` (seconds per action, `batch` crafts per session, `time_value` copper per hour of play, run speed, detour; `config_from_dict` strict, `config_from_json` lenient, `config_changes` what is stored), `CityMap` (locations in yards, vendors' stock and the faction each vendor's prices follow (`vendor_reputations`, `sellers`, `reputation_of`), hub, `overrides`, `zone`: its zone map's world box and AreaTable `area` id, for map coordinates; `from_dict`, `seconds`, `nearest`, `vendor_for` (optionally among some sellers), `trip`; memoized, shared across threads), `ANYWHERE` (the one-spot city when a version has no presets), `station_kind` (a SpellFocusObject name as a location kind), `Block`/`route`/`time_blocks` -> `Timing` (fixed and per-craft seconds, `breakdown`, `legs`, `unsold`, `missing`, `per_hour`)
- `src/altarmy_profit/cities.py` – pure builder of city presets (`CITY_SPECS`, `build_city`) from vmangos spawns (`vmangos.city_centre`, `npcs_near`, `objects_near`, `vendor_stock`, `vendor_factions`: a preset's `vendor_reputations` name the city-faction vendors' factions); `scripts/build_cities.py` writes `data/forever/cities/*.json`, keeping each preset's hand-tuned `overrides`; `scouted_mailboxes`/`add_scouted_mailboxes` add the mailboxes the user's frellscout addon (`../frellscout`) recorded in game to those `overrides` (`scripts/import_mailboxes.py`), skipping any within 10 yd of a known one (vmangos has only Classic's)
- `src/altarmy_profit/talents.py` – the Legacy talents (WoW: Forever) that change profits, by spell id (`LEGACY_TALENTS`: Master Chef, Bartering); `extra_results`/`vendor_discount` turn a character's (spell id, rank) pairs into `engine.Crafter` fields, `known` lists them for the API
- `src/altarmy_profit/reputation.py` – pure: the reputations that change vendor prices, `CITY_FACTIONS` (the eight home factions by `Faction` id: the six cities' plus Gnomeregan Exiles and Darkspear Trolls, whose vendors stand in other cities); `city_standings` keeps a character's standings with those, `vendor_discounts` turns them into (faction, percent) by a version's schedule
- `src/altarmy_profit/luasv.py` – pure generic parser for SavedVariables files (`Name = <Lua table>` statements); nesting capped at `MAX_DEPTH`
- `src/altarmy_profit/altarmy.py` – pure reader for the Alt Army addon's `AltArmy_TBC.lua`: characters, professions, learned recipe ids (= `recipes.spell_id`); characters are keyed by GUID since the addon's character data v3 (by name before), so the name is the entry's `name` field (the full name), else the key; entries with the same `guid` or name are one character, the newest `lastUpdate` winning (a bare first name, which pre-v3 addons saved for every "First Surname", is not matched); never-scanned stubs (no name, class or faction) are skipped; `Character.reputations` are the entry's `Reputations` standings with the city factions; `groups` by realm/faction, `crafters`
- `src/altarmy_profit/store.py` – `load_market(conn, game_version, auction_house_id, ah_cut=, mail_postage=)`: database rows to engine dataclasses; characters (`save_characters` replaces all, `upsert_character`/`delete_character` one) and AH blocks per user and version; `profession_names` (without `HIDDEN_PROFESSIONS`: class skills and a test line DB2 gives recipes)
- `src/altarmy_profit/ratelimit.py` – pure in-memory sliding-window `RateLimiter` (per instance), `Limits`/`HOSTED_LIMITS` (per IP 300/min, per uid 120/min), `client_ip` (first `X-Forwarded-For` entry: right through Firebase Hosting, spoofable on the direct run.app URL)
- `src/altarmy_profit/service.py` – web use-cases (every per-user function takes `user_uid` after `conn`): `MarketCache` (per version, one `Market` per auction house; rebuilt after `invalidate()` or when `store.market_stamp` (build, `game_versions.loads`: bumped by every `db.set_build`, so loading the same build again counts (revision 0018), newest snapshot id, `price_version`) moved, checked at most every `STAMP_TTL` s, so other instances' uploads, the ingest job and the merge show up); `RankCache` (the last 64 full rankings, valid only for the very `Market` they were ranked on; `/api/rank` slices `top` from it, so paging doesn't re-rank); `search` over the selected realm/faction's characters (`engine.recipes_for_characters`: learned recipes, plus with `unlearned` "train" those a character can train: taught by one of the chosen `sources` (`Recipe.source`: trainer, recipe, bop) and needing at most `look_ahead` (0 to `MAX_LOOK_AHEAD`, 50; the slider steps by 5) more skill than they have (`engine.Learning`, `engine.can_learn`, `Recipe.required_skill`), or with "all" every recipe of their professions whatever teaches it: the search's Recipes radio and its sub-options; chains only sub-craft through those; without characters every recipe, for one unnamed crafter), selling only via the allowed exits and keeping what an `engine.Filters` (min/max cost, profit, ROI) accepts; `evaluate`: one recipe with the user's `choices`; both plan per group of cities that charge the characters differently and keep each recipe where it pays best (`city_groups`, `best_of`, `city_worth`; see Reputation discounts); realm/faction `selection` (saved if it has characters or an auction house, else the biggest group, else `prices.freshest_auction_house`) and its auction house (`selected_auction_house`); `select` takes a group or any named auction house; `replace_characters` (imports: forgets a selection the new characters aren't on), `delete_character`; `data_version`/`bump_data_version`; game data update (`update_game_data`, the ingest job's `--only-if-new`)
- `src/altarmy_profit/api.py` – FastAPI JSON API (`create_app(game_versions, database=..., verifier=, firebase=, limits=)`: one shared `Database`, a market cache per version; the Firebase project comes from the environment unless given; tests pass a fake `verifier`); also serves the built `frontend/dist`. Dependencies: `CurrentUser` (the bearer Firebase ID token, 401 without; every route but the public ones, uploads included: the watcher and Alt Army Sync send their email sign-in's ID token; guests get everything, and there is no level gate for now). `DELETE /api/me` deletes the user's rows and, in the same transaction, the Firebase user. The API rate-limits per client IP (middleware) and per uid (in `CurrentUser`), 429 with `Retry-After`; every /api response carries `Cache-Control: no-store` (Hosting's CDN). `create_app` builds its default `Database` with `migrate=False` (`serve` passes one that migrates). Public: `/api/config` (the Firebase web config, with the emulator's URL in development), `/api/versions`. `POST /api/uploads` (multipart `file`, `kind`, `modified_at` ms, `via`; plain or gzipped; 400 bad file or an Auctionator file for Forever, 413, 429; every outcome in `uploads`; `UploadResult.realms` lists the auction house scans an Alt Army file recorded), `POST /api/uploads/paste` (JSON `text`: the addon's export; recorded as kind `altarmy`, via `paste`; 400 for another game's export), `GET /api/uploads`; `/api/me`; `/api/coverage` (each realm's last scan: the realm picker and its price freshness). `ItemInfo` carries `ah_price` (the cheapest listing), `ah_sell_price` (what the AH exit counts), `ah_quantity` (units listed) and `ah_levels` (the first `LEVELS_SHOWN` price levels; `counted` False for a level plans don't count on); `RankResult.slow` flags an AH sale that may take over `service.SLOW_DAYS` (`days_to_sell`: the units listed at or under the sell price plus the plan's, at the item's `sale_rate`) or, with no sale rate, one resting on few listed units (`service.slow_to_sell`, `thin_market`; the results table's ⚠, informational), and `short` the units bought beyond what is listed (◔), from the listings `MarketCache.get_priced` caches with each market (`store.Priced`). Every per-game route takes a required `game_version` query parameter (the `State` dependency); `GET /api/versions` lists them. The front end serves Forever only: `lib/gameVersion.ts`'s `GAME_VERSION` constant is sent with every request and put first in every query key after the route name. The front end polls `GET /api/status` (every 30 s and on window focus); its `data_version` and `price_version` (the selected auction house's) together are `useDataVersion()`, part of the characters/rank/evaluate/prices query keys. `components/PriceSignal.tsx` (in `SearchTab`) listens to the selected house's price signal (`lib/signals.ts`, Firestore SDK loaded lazily on `lib/auth.ts`'s `firebaseApp()`), refetches the status when the signal's version passes the shown one, and shows a "Prices updated" notice whenever the shown version moves for the same house. `/api/rank` and `/api/evaluate` take the `price_version` the front end knows, and `MarketCache.get(ah, at_least=)` then skips `STAMP_TTL`, so a refetch right after a signal never gets a market built before the new prices. The detailed step list's "Run to …" lines show the zone map on hover (`components/ZoneMap.tsx`: `frontend/public/maps/<LocationOut.map_area>.jpg`, `lib/wow.ts` `zoneMapUrl`, with a dot at `map_x`/`map_y`). The expanded row (`SessionDetails`) sums the session up in three lines (crafts, investment and net profit; estimated time and per hour; expected skill points, with characters) and, when several characters could craft the recipe, offers a Crafter pick (names in class colour) that plans with `/api/evaluate`'s `crafter` (`Market(final_crafter=)`: that character does the final craft, even a grey one). `POST /api/evaluate` re-costs one recipe with the choices the user made in its flow chart or step list (both use `components/ChoiceMenu.tsx`; each step's `paths` name the tree nodes it stands for, several when merged, and `lib/steps.ts` maps them back; `ResultsTable` holds the choices per recipe, `lib/choices.ts`; the row then shows the changed plan until Reset). `GET /api/rank` and `/api/evaluate` take `skill_crafters` (the characters being skilled up: only the lowest-skilled of them in the recipe's profession who qualifies does the final craft, `Market(skill_crafters=)`; in the rank cache key). `GET /api/rank` takes `exits`, optional bounds (omitted = unbounded) and `professions` (the bounds and the profession filter narrow the cached, unbounded ranking, so they are not in the rank cache key; browsing without characters shares one cache entry across users) and returns the first `top` results plus `total`; the search pages through them 50 at a time. `GET /api/professions`; `DELETE /api/characters?realm=&name=`. `CharacterOut.vendor_discounts` lists what a character's standings take off at whose vendors (shown in `CharacterList`), and `StepOut`/`NodeOut` carry `rep_discount` and `rep_faction` (`lib/talents.ts`' `discountNote` names them beside Bartering). `Me.admin` and the `AdminUser` dependency (403 unless the admin claim): `GET /api/admin/ingestion` (per version: each scheduled job's newest run and `late`, recent runs, every user's uploads (`uploads.recent_all`, `uploads.stats`), snapshots per source (`prices.snapshot_stats`), `can_run`: the jobs Run now can start, `["ingest"]` with a launcher), `POST /api/admin/jobs/ingest` (202; Use the project venv (`.venv`); do not install packages globally. If it is missing: `python -m venv .venv`, then `.venv\Scripts\python -m pip install -e ".[dev,ui]"` (add `,tray,build-tray` for Alt Army Sync). Front-end packages live in `frontend/node_modules` (`npm ci` in `frontend/`); the root `package.json` only holds dev tooling (`npm ci` in the root).

- Deploy: see README's "Deploy" (Git Bash). Creating, changing or deleting cloud resources is visible and billed: show the command and get the user's OK first; read-only gcloud is fine.

## Conventions

- **User-facing text says "upload", never "import"**, for characters and scans alike (Upload your characters, Auto-upload, Characters uploaded). Code identifiers such as `AutoImport.tsx`, `onImported` and `auto_import_at` keep their names.
- **Money is integer copper** everywhere (prices, costs, profit), including the JSON API. Format only at the display edge: `format_money` in Python (CLI), the `Money` component (`frontend/src/components/Money.tsx`, coin icons) in the front end.
- **Admins are a Firebase custom claim** (`admin: true`, set with `altarmy-profit admin grant <email>`), never a `users` column or an HTTP route; a token shows a grant once it is refreshed (sign out and in). Admin routes take `AdminUser`. Against the Auth emulator (`FirebaseConfig.emulator_host`, i.e. `npm run dev`) every user is an admin; `npm run dev:staging-auth` uses the real claim.
- **User state is per user**: characters, `user_settings` and `ah_blocked` carry `user_uid`; store/service/users functions take it right after `conn`. Never gate on tier inside service code: tiers are the API's dependencies. The `"local"` users row that revision 0002 creates is a leftover of the removed local mode (`local_sync`, unused, is dropped by the next revision).
- **Uploads are untrusted**: on bad input the parsers must only raise `ValueError` (the API's 400); `test_mangled_files_only_raise_value_error` fuzzes them. Never store an uploaded file.
- **Migrations run once per deploy** (`altarmy-profit migrate` as a Cloud Run job, before the service); hosted instances never migrate. Keep revisions safe for the previous release's instances still serving (additive first).
- API handlers are plain `def` (FastAPI runs them in a threadpool) and open their own connection per request (`database.begin()`); never share a connection across threads.
- **Storage is SQLAlchemy Core** (no ORM) against `schema.py`, and must work on SQLite and Postgres: no raw SQLite-only SQL (`INSERT OR REPLACE`, `PRAGMA`) outside `db.py`'s engine setup; use `db.upsert`. Functions taking a `Connection` never commit: the caller owns the transaction (`Database.begin()` in the API and CLI; tests use an autocommit connection). Order query results explicitly; row order is not insertion order on Postgres.
- After changing API models or routes, regenerate `frontend/openapi.json` and `frontend/src/api/schema.d.ts` (`check.py` does this) and commit both.
- **Keep `engine.py` pure**: no file, DB or network access. Load data in `store.py` and pass plain dataclasses in.
- **Type annotations are required**; mypy runs in strict mode over `src` and `tests`, and the front end uses TypeScript `strict`.
- Prefer red-green-refactor: write a failing test first, then make it pass. Ingest tests use fixture CSVs, never the network. API tests use FastAPI's `TestClient`; front-end tests use vitest + Testing Library with `fetch` stubbed (`frontend/src/test/utils.tsx`).
- Line length is 110; let `ruff format` handle style.

## Data gotchas

- Development and tests keep **one SQLite file** (`data/altarmy-profit.sqlite`) for both versions, the same schema as Postgres. Game data is keyed by `game_version`; `user_settings` (selection, `data_version`), characters and `ah_blocked` by `user_uid` and `game_version`; item and recipe ids are only meaningful within one version. The pinned/loaded build is `game_versions.build`. `recipe_reagents.slot` keeps DB2's reagent order, which the flow chart's choice paths (`r.0`, `r.1`) depend on.
- Disenchant results are server-side loot data and are **not** in DB2. Without a version's `disenchant.csv`, disenchant is ignored. Do not invent drop tables. Which items can be disenchanted is in DB2: ItemSparse `Flags_0` bit `0x8000` (NO_DISENCHANT: Enchanting's wands, PvP rank gear) makes `items.disenchantable` False (revision 0016; true in older databases until the next game data update), and `Market._disenchant_rows` gives such an item no disenchant exit.
- **Arcane Salvager** (WoW: Forever; Enchanting recipe spell `service.ARCANE_SALVAGER_SPELL` 1263056): near it a disenchant has `engine.ARCANE_SALVAGER_BONUS` (10%, the players' understanding, unverified) chance of a second roll of the same table. `/api/rank`'s and `/api/evaluate`'s `arcane_salvager` (in the rank cache key) -> `Market(arcane_salvager=)` scales `_expected`, so every disenchant value, its `Material.value`s and flips are 1.1x; a `Material`'s counts still describe one roll. No station trip is timed. `Characters.arcane_salvager` (`service.knows_arcane_salvager`: any uploaded character knows the recipe) is the UI's default.
- **Essence conversions** (`recipes.kind` `convert`, revision 0017; `Recipe.is_conversion`): an item's Use effect that consumes it and casts a spell creating another item, its reagents (if any) more of the same item, both items disenchant results (`ingest.conversions`; so none without `disenchant.csv`). Id `ingest.CONVERSION_ID_BASE` + spell id, skill line 0, skill name "" (left out of `profession_names`), input count 1 + the spell's reagents. Anyone converts (`crafters_of`, `recipes_for_characters`), it never skills up (`can_skill_up`, `expected_skill_ups`), `Market.rank` skips it without `include_trivial` or with `skill_crafters`, and `Market._sell_kinds` sells it only when `disenchant` is an allowed exit, then on the AH whether or not `ah` is. Chains use it as a `craft:<id>` option (always); `_craft` buys a conversion's input only (no chain below it, which would go round in circles). `Node`/`Step`/`Option.convert` and `RankResult.kind` tell the UI to say Convert.
- **Buy-and-disenchant flips** (`Recipe.kind` `flip`, `Recipe.is_flip`; `Recipe.anyone` covers both no-profession kinds): `Market` makes them itself (`_flips`, replacing any in the recipes it is given, so narrowed markets agree), one per item with `_disenchant_rows` that can be bought on the AH (`_listed`: its counted ladder's units, else 1 with a plain price), id `engine.FLIP_ID_BASE` + item id, reagents `((item, 1),)`; never in the database or `_by_output`. `evaluate` caps a flip's crafts at `_listed` (no `short` units), `_sell_kinds` allows only `disenchant` (and only when allowed), `_craft_seconds` is 0, `plan_steps` emits no craft step for its root and `Node.flip` lets the flow chart sell the bought node directly. Otherwise as conversions: anyone, no skill-ups, skipped when skilling up.
- **Enchants cast for the skill point alone** (`recipes.kind` `enchant`, `Recipe.is_enchant`; no migration: the kind is free text): a profession spell with reagents and SpellEffect `Effect` 53 (`ingest.EFFECT_ENCHANT_ITEM`) that creates no item, stored with `output_item_id` 0 and output count 1, otherwise as a craft (SkillLineAbility id, trivial ranks, `learn_skill`, `source`). Forever has 179 for Enchanting and 3 for Engineering. It is a profession's recipe (not `Recipe.anyone`: learned or trainable like a craft), never in `_by_output`, and its only exit is `engine.SKILL_EXIT` (`skill`, value 0, not among `ALL_EXITS`), which nothing else has: `Market._sell_kinds` allows it only when `skill` is among the market's exits, so enchants rank only where asked for. Revenue 0, profit = −cost, ROI −100%; `_final_crafters` always keeps only crafters it can skill up (whatever `include_trivial` or a `final_crafter` say); `plan_steps` ends with the cast (no sell step), the root `Node` and its craft `Step` are named after the spell with `enchant` set. `/api/rank` and `/api/evaluate` take `skill` in `exits`; `RankResult.kind` `enchant` has `output_name` = the spell's name. The rod an enchant needs and the item enchanted are not modelled. In the UI the Sell via group gains "Enhance item for skill up only" (`SearchTab`'s `SKILL_ONLY`, stored apart as `altarmy-profit.search.skillOnly`, default off) only while the setup skills up Enchanting or Engineering itself (`SKILL_ONLY_WHY`, each with its tooltip; not Any profession), and only then is `skill` sent; `ResultsTable` says "Skill only", the step list "Cast … N times", and the flow chart has no sell node.
- DB2 does not say which vendors sell which items. `data/<version>/vendor_items.csv` (unlimited stock, no condition, no token cost, spawned vendor) says which; the per-unit price is `items.buy_price / items.buy_count` (DB2 `BuyPrice` / `VendorStackCount`), rounded up. The engine buys each reagent from the cheaper of vendor and AH (ties go to the vendor). DB2's `BuyPrice` is set on nearly every item, so it alone does not mean a vendor sells it.
- `recipes.min_skill` currently comes out as 1 for every real recipe, so do not rely on it. The skill a recipe is learned at is `recipes.learn_skill`: the RequiredSkillRank of the recipe item teaching its spell (ItemEffect trigger 6, `ingest.learn_skills`; about 3/4 of Forever's recipes), 0 for trainer recipes, whose requirement DB2 lacks: `Recipe.required_skill` then falls back to `trivial_low` (yellow, never below the real requirement). It reads 0 in older databases until the next game data update. What teaches a recipe is `recipes.source` (revision 0019, `ingest.learn_sources`): `recipe` when an item teaching its spell can be traded or is one a vendor sells (Forever binds most vendor-sold recipes on pickup; `data/forever/vendor_recipes.csv` lists the recipe items spawned vendors sell without a condition, limited stock included, and `vendor_items.csv`'s count too), `bop` when every such item binds on pickup or is a quest item and no vendor sells it (looted or earned: 657 of Forever's 2025 crafts), `trainer` when no item of the game teaches it (ItemEffect also names items ItemSparse lacks: they teach nothing); `trainer` in older databases until the next game data update. Recipe output count comes from `SpellEffect.EffectBasePointsF` and is only spot-checked. `recipes.cast_time_ms` (SpellMisc -> SpellCastTimes, the DifficultyID 0 row) and `recipes.station` (SpellCastingRequirements' SpellFocusObject name as `timing.station_kind` spells it: anvil, cooking_fire, loom, ...) read 0 and "" in older databases until the next game data update. WoW: Forever adds stations vanilla never had (spinning wheel, sewing machine, tanning rack, loom, master forge, iron oven, alchemy lab, ...): vmangos has no positions for them. Until we learn how they work they are `timing.DEPLOYABLE`: set down where the crafter stands, so never a trip and never `missing`; `Timing.deployed` lists them and the UI names them.
- **Rankings are sessions.** With a time model, `service.search` ranks each recipe as a session of the user's `TimeConfig.batch` crafts (`Market.rank(crafts=)`, timed by `service.session_model`: batch 1, the whole session at once), so cost, revenue, profit, steps and tree are the session's, the bounds apply to them, and `RankResult.details` spells out the route; `/api/evaluate` without `copies` or `city` gives exactly the ranked result (with the user's choices), so the expanded row (`SessionDetails`) shows its own result and asks the server only for other copies or another city. Without a time model (CLI `rank`) a result is one craft.
- **Profit per hour.** In the engine, seconds are per craft of the evaluated recipe (a session's time model has batch 1, so per session): a batch clicks once per whole stack and sends whole mails (`Market._stacks`: one salt a craft is one stack-click per batch of 20), and those clicks, trips from the hub, AH searches and character switches are divided by `TimeConfig.batch`. The per-user time settings are `user_settings.time_city`/`time_config` (JSON of the changes from the defaults), read by `service.time_model` (the saved city if the selection's faction crafts there; else, the default, "wherever pays best": `TimeModel.fastest` holds the faction's cities and `Result.timing` is the quickest of them that has every station the plan needs, while `service.default_city`, Orgrimmar/Stormwind, only guides the estimate plans are chosen by; `timing.ANYWHERE` without presets). That is the whole choice while the cities charge the characters the same; where they don't, see Reputation discounts. `/api/rank`'s cache key includes `TimeModel.key`; `sort=rate` sorts the cached ranking (`service.by_rate`, cached as its own entry), timing every result once; `sort=skill` likewise (`service.by_skill`: cheapest expected skill point first, from `engine.skill_up_chance`: 1 while orange, falling evenly from yellow to 0 at grey; `Result.skill_chance`, the first craft's; `skill_ups`, the session's from `engine.expected_skill_ups`: craft by craft at the skill the crafts before are expected to have reached, never past grey or the cap). `RankResult.cities` gives the recipe in each of the faction's cities (never neutral towns: Booty Bay's, Gadgetzan's and Everlook's auction house is not the one prices track, so there are no presets for them), each with its own `profit`; `best_city` is the one worth most (`service.city_worth`) without `missing` stations. Presets load lazily per version (`AppState.cities`; a restart rereads them).
- **Reputation discounts.** A vendor charges a buyer less for their standing with the vendor's faction: `GameVersion.reputation_discounts` (Forever: vanilla's 10% from Honored, nothing more at Revered or Exalted), added to Bartering's percent and the unit price rounded up (`engine.vendor_price`; adding rather than multiplying is an assumption until a Forever vendor's price is compared; vanilla's further 10% for PvP rank 3 is not modelled). Only the eight city factions count (`reputation.CITY_FACTIONS`). The addon saves every reputation (`Reputations[factionID].s`); the site keeps those eight from a file upload, the export sends only them as `R|` lines, and `character_reputations` (revision 0015) stores the standing itself, so a change of the schedule needs no re-upload. A faction not listed is Neutral. The vendor's faction is per vendor, not per city (`vendor_reputations` in the presets, from vmangos: gnome vendors in Ironforge and Stormwind, troll vendors in Orgrimmar; a vendor of any other faction discounts nothing), so the price needs a city: `Market._vendor_unit` takes the best discount among the time model's city's sellers of the item (`Node.rep_discount`, `Step.rep_discount`), and the route buys at a vendor who gives it (`engine.vendor_holders` into `Block.vendor_sellers`). Without a time model (CLI `rank`) or presets (TBC) nobody gets one.
  - **The city is chosen by copper per hour.** Left to pick the city, `service.search` and `service.evaluate` group the faction's cities by what their vendors charge the characters (`city_groups`, `engine.city_prices`) and plan with one `Market` per group (`TimeModel.fastest` = the group). Without standings that count there is one group: the plain path, at its cost. Otherwise only recipes that can involve a differently priced vendor item are planned in every group (`engine.recipes_using`; about two thirds of them, so a cold ranking costs up to about three times one city's), and `service.best_of` keeps each where it is worth most (`city_worth`: a city with every station, then a plan that profits, then copper per hour, else the smallest loss, then the quicker), the others on `Result.alternatives`. A recipe whose plan comes out the same in every group is one result timed lazily across all cities, as before. `/api/evaluate` does the same, so it still gives exactly the ranked result.
  - A saved city, or `/api/evaluate` with `city`, plans and prices in that city alone. `RankResult.cities` then says what the same plan makes elsewhere with its vendor buys at that city's prices (`engine.cost_in`); picking the city re-plans there.
  - The faction a discount is named after (`StepOut.rep_faction`) is worked out for the city the result is timed in (`engine.reputation_faction`), since one plan serves every city of its group.
- Item tooltips (`store.load_item_details`, `/api/rank`'s `items` map) use denormalized `items` columns filled at ingest: subclass names from `ItemSubClass`, icon names from `ManifestInterfaceData` (`Interface\Icons` only; the browser loads them from wow.zamimg.com). Stats, armor and weapon damage are computed at ingest (ItemSparse holds only stat allocations: `itemstats.py`) and stored rendered: `items.armor`, `dmg_min`/`dmg_max`/`dps`, `stats` (JSON list of white lines) and `effects` (JSON `[{trigger, text}]` green lines); `ItemInfo` carries them and `ItemLines` prints them in game order. Databases from before a column read 0 / empty until the next game data update.
- Re-running `altarmy-profit ingest` rebuilds that version's items, recipes and disenchant rows but leaves prices, users and their characters, settings, `ah_blocked` and the other version alone.
- **`auction_houses.price_version`** moves whenever the house's prices changed: `prices.record_snapshot` bumps it when it moved a current price (not for a quarantined or news-less scan), the merge when its 7-day columns changed. It is in `store.market_stamp`, `/api/status`, and the Firestore price signal.
- **Prices are per auction house** (`auction_houses`: version, realm, faction; faction `""` = one shared by both factions (none on Forever since revision 0009: its houses are per faction); realm `""` = the unnamed one, for prices set without a realm). A selection's auction house is its faction's, else its realm's shared one (`prices.find_auction_house`). Sources: Alt Army's scans (`altarmy`, Forever), Auctionator uploads (TBC), manual/CSV. Forever reads only `altarmy` and hand-set snapshots (`prices.FIRST_PARTY`); revision 0014 deleted what AHledger and Auctionator had recorded for it. Every source records a `price_snapshots` row; `price_observations` get only news and move `price_current`, which the engine reads; the newest `seen_at` wins whatever the source, so a manual price holds until a later scan, and a price from another source replaces a scan's ladder. An Auctionator item was seen at the scan time if its last day is the scan day, else at the start of that day; an Auctionator key ending in the faction means a split house. `price_daily` comes from Auctionator's h/l/a or a scan's market price and is pooled across uploaders (min low, max high, max available). Observations older than 180 days are pruned after each upload and by the prune job; snapshots `price_current` points at are kept. Money columns for prices are `BigInteger` (copper exceeds 2^31).
- **The order book (Forever).** An Alt Army scan lists every auction; the addon pools them per item into price levels (unit price = buyout over count, rounded up; listings without a buyout are counted only; items are keyed by item id alone, so random-suffix gear shares its base item's ladder; sellers are never stored). `price_current.ladder` holds the newest scan's ladder (`book.encode`), `listed` whether that scan had the item (an item missing from a scan is unlisted: no AH buy option, and it sells at what it used to go for), `market_price` the price 15% into the listed units. Only complete scans exist: the addon drops one the auction house closed on. A level's `age` counts the scans it survived; a level of age 0 under half the 7-day median is left out of what plans buy (a stray cheap listing is gone before anyone gets there) but shown in the item's tooltip. Sales are inferred between two scans at most 30 minutes apart (`book.sold_between`); an emptied market says nothing (counted as cancelled). The scan's time is the game server's (`GetServerTime`), so no local day is compared.
- **Buy vs sell price.** Forever: reagents are bought up the item's ladder (`Market.books`; `Market.prices` holds its cheapest counted level), and a craft sells at `prices.book_sell_price`: the lower of the market price (while listed) and what the item goes for (`sale_price`, else `median_7d`). TBC and hand-set prices: `Market.prices` is `price_current.price`, the cheapest listing, and `Market.sell_prices` the lower of `price` and `median_7d`, except for `manual`/`csv` snapshots, used as they are. `median_7d` is the median of the item's daily medians over its latest 7 days with data within 30 days (not 7 calendar days: one player's sparse scans would leave a lone spike as the only sample); `scans_7d` counts those days. `price_daily.median` = median of the day's low, high and that UTC day's accepted scan prices (clamped). The merge fills them; until then the sell price is the price. `sell_cap` and `feed_tables` are unused since revision 0014 and dropped by the next revision.
- **Quarantine.** Only uploads are screened (`trust=None` records a scan unscreened). A scan is quarantined when at least 20 of its fresh prices (an Alt Army scan's market prices) can be compared with a baseline (`median_7d` with `scans_7d >= 3`) and more than `0.1 + 0.2 * trust` of them are over 4x off either way (real TBC scans: at most ~5%). An Alt Army scan taken at most 30 minutes after another is also quarantined when it has under a quarter of that scan's price levels (`prices._breaks_off`, from 50 levels on; the share is a guess until real pairs of scans are measured). A quarantined snapshot is a `status='quarantined'` row only: no observations, no `price_current` or `price_daily` change; the merge ignores it.
- `ah_blocked` holds items the user never wants sold on the AH (per game version, not per realm; set from a search row's ⋯ menu, listed on the Manage page, `/api/ah-blocked`). It is passed per request as `Market(no_ah=...)`, which drops only the `ah` exit for those items: they can still be bought on the AH, and disenchant materials are still valued at AH prices. The cached base market never holds it, so toggling needs no cache invalidation.
- `favorite_recipes` holds the recipes the user marked as favorites (per user and game version; a search row's ⋯ menu, `/api/favorites`). `/api/rank` moves them to the front after filtering and before slicing `top` (`service.favorites_first`), so they are not in the rank cache key; `ResultsTable` keeps them first under any column sort and rings their rows (`.favorite`).
- Alt Army recipe ids are craft spell ids. On TBC clients one recipe is stored under several alias keys sharing a `primaryRecipeID`; Enchanting rows carry only `color`. Auctionator (TBC's price source) keys realms as the realm name without spaces, plus the faction where auction houses are split (`Dreamscythe Horde`); `service.match_auctionator_realm` maps a realm/faction to it, and the key is stored as a `realm_aliases` row. Auctionator's day numbers count from 2020-01-01 in local time; it drops days older than its history setting, and random-suffix gear (`gr:` keys) is skipped.
- Characters and mail: `Market` gets the selected characters as `engine.Crafter`s and costs every craft *at a character* (`Market._obtain`): each reagent is bought there, or crafted by any character who can (learners, or with no learner, whoever `unlearned` lets: `engine.can_learn`) and mailed over if that is someone else. The final crafter is whichever gives the best profit. Postage is `MAIL_POSTAGE` (30c) per attachment, one stack each (`items.stack_size` from `ItemSparse.Stackable`; older databases read 1 until the next game data update). A disenchant is free if the final crafter enchants, else the output is mailed to the best enchanter; with no enchanter at all the disenchant exit is dropped. Postage is in `cost` and shown as `mail` steps and flow nodes; steps carry `who`. `engine.plan_steps` (a `Result`'s `steps`, planned when first read, so a ranking never schedules results nobody looks at) orders them dependencies first and then per character (`engine._schedule`): each does all their buys, then crafts, then mails before another takes over, whoever can finish outright first, so a character is revisited only for what waited on someone's mail. Without crafters (CLI `rank`, or browsing without characters on the web) one unnamed character does everything, so nothing is mailed; the results table shows "anyone" as the crafter. Costs are whole batches (spares from multi-output crafts are not credited). Soulbound items (`Item.tradable` False: `items.bonding` 1 or 4) are never mailed, so only the character who needs such an intermediate crafts it, a soulbound craft is disenchanted only by its crafter, and it gets no AH exit. One `Memo` serves a whole `rank()` (keyed on item, quantity, character and depth, not the ancestors): chains stop at `MAX_CHAIN_DEPTH`, which also ends cycles, and a recipe consuming its own output is skipped.
- Legacy talents (WoW: Forever): the addon saves `legacyTalents.spells[spellID] = rank` (data version 2; v1 data without `spells` was the class-talent config and is ignored) and exports `T|` lines. They are stored in `character_talents`, kept on `Character.talents`, and mapped by `talents.py`:
  - **Bartering** (1225459, 5% per rank, 2 ranks) makes that character's own vendor buys cheaper: the unit price is rounded up, and the discount is on `Node.discount` and `Step.discount` (a reputation discount, which adds to it, is on `rep_discount`). Nobody buys on a barterer and mails the goods on.
  - **Master Chef** (1225457, 10% per rank, 5 ranks) gives the final Cooking craft `output_count + chance` expected units in its revenue, reported as `Result.bonus_output` and the sell `Step.bonus`. Sub-crafts get no bonus, and postage on the extras is not charged.
  - The DB2 source is `TraitSystem` 45 with trees 1187-1189 (see the addon's research doc).

TBC's SpellEffect leaves `EffectBasePointsF` at 0 and encodes counts as `EffectBasePoints` + a 1..`EffectDieSides` roll. Downloaded CSVs are cached under `cache/` (git-ignored, as is `data/*.db`).
