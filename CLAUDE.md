# CLAUDE.md

Conventions for AI agents working in this repository.

## Project

`altarmy-profit` is a local Python tool that finds profitable crafting recipes and production chains for **World of Warcraft: Forever**. Items and recipes come from client DB2 tables (wago.tools CSV exports) loaded into the database (SQLite locally, Postgres for the planned hosted app); auction house prices come from addon scans, CSV or by hand; the engine ranks recipes by profit (buy or craft reagents, then sell via vendor, AH minus the 5% cut, or disenchant). See `README.md` for usage and roadmap.

## Layout

- `src/altarmy_profit/versions.py` – the game versions (`tbc` TBC Anniversary, `forever` WoW: Forever): each `GameVersion` names its `data/<version>/` data files, wago.tools product and pinned build, interface number, WoW flavor folder (`_anniversary_`, `_classic_beta_`), level and skill caps (`max_level`, `max_skill`: bound hand-made characters), AH cut and postage
- `src/altarmy_profit/db.py` – `Database(url)`: the engine factory (SQLite or Postgres via SQLAlchemy Core), migrated to the newest Alembic revision and `game_versions` and the local user registered on first use; `default_url()` (`DATABASE_URL`, else `data/altarmy-profit.sqlite`); `Database(url, migrate=False)` never migrates (hosted instances: the deploy's migrate job does, and `upgrade` holds a Postgres advisory lock); pool sizes from `DB_POOL_SIZE`/`DB_MAX_OVERFLOW`; `upsert` (dialect-specific ON CONFLICT), `LOCAL_UID`, build and row-count helpers (settings live in `users.py`)
- `src/altarmy_profit/schema.py` – every table as a Core `Table` on one `MetaData`; `src/altarmy_profit/migrations/` – Alembic env and revisions (`alembic.ini` at the root for the CLI); `tests/test_migrations.py` checks they match `schema.metadata`
- `src/altarmy_profit/auth.py` – `User(uid, tier)`, `LOCAL_USER` (uid `db.LOCAL_UID` = "local", linked), `user_from_claims` (tier `free` iff the Firebase `sign_in_provider` is `anonymous`), `mode_from_env` (`ALTARMY_MODE`: local | hosted), `FirebaseConfig.from_env`, the `TokenVerifier` and `AccountAdmin` protocols and `FirebaseVerifier` (firebase-admin, the `hosted` extra; verifies tokens and deletes users; honours `FIREBASE_AUTH_EMULATOR_HOST`)
- `src/altarmy_profit/users.py` – `ensure_user` (row on first sight, follows tier changes, sets `linked_at`), `delete_user` (cascades; nulls `price_snapshots.uploader_uid`), typed `UserSettings` (selection, `data_version`) and `LocalSync` (local mode's addon paths, mtimes, sync times), each per (user, game version); API keys (`create_key` returns the `ak_…` key once, only its SHA-256 is stored; `user_for_key`, `list_keys`, `revoke_key`); `trust`/`adjust_trust` (`users.trust_score`: halved per quarantined scan, +0.1 per accepted screened one)
- `src/altarmy_profit/uploads.py` – uploaded addon files: `ingest` (Alt Army replaces the uploader's characters via `service.replace_characters`; Auctionator records every realm with prices, each key resolved alias first, then the uploader's matching character group, then parsed), `scan_time` (file mtime clamped to 30 days), `decompress` (gzip, `MAX_BYTES` 32 MB), `record_upload`/`recent` history, `check_rate` (`RATE_LIMIT` 60/hour); each realm's Auctionator scan is screened with the uploader's trust (`RealmPrices.quarantined`, "not used" in the detail; the upload stays `accepted`)
- `src/altarmy_profit/watch.py` – the CLI watcher (`altarmy-profit watch`, no database): `find_files` (both versions, Alt Army first; `version_of` by flavor folder), `changed` against a JSON state of mtimes, gzipped multipart over urllib (`Transport` injectable), `sync_once`, `run` (backoff; stops on `BadKey`); standard library only (the WoW folder finders live in `wowfiles.py`, re-exported by `prices`)
- `src/altarmy_profit/paste.py` – pure decoder of the Alt Army addon's export string (`AAX1:` + LibDeflate's printable encoding of raw DEFLATE of `V|`/`C|`/`P|`/`T|` lines (`T|<spell id>|<rank>`: a Legacy talent); `decode`, `Export.game_version` from the client's interface). The addon's `AltArmy_TBC/Data/ProfitExport.lua` (repo `../altarmy_tbc`) writes it; `tests/fixtures/altarmy_export_v1.txt` is a copy of the addon's golden `spec/fixtures/profit_export_v1.txt`, so change both together
- `src/altarmy_profit/tray.py`, `tray_core.py` – the Windows tray uploader (`altarmy-profit-tray`; the `tray` extra: pystray, Pillow): the watcher in a thread, key dialog (tkinter), Start with Windows (HKCU Run), one instance per user; `tray_core` is its pure, tested part (`~/.altarmy-profit/tray.json`, status line, autostart command). `scripts/build_tray.py` (the `build-tray` extra) makes `dist/altarmy-profit-tray.exe`; `.github/workflows/tray.yml` publishes it as a GitHub Release on a `tray-v*` tag, and the Manage page links the latest
- `src/altarmy_profit/legacy.py` – imports older releases' SQLite files (`data/altarmy-profit-<version>.db`, and the pre-versions `data/altarmy-profit.db`) into the database once, as the local user's, then renames them `*.imported`; `cli.main` runs it when `--db` isn't given
- `src/altarmy_profit/ingest.py` – download DB2 CSVs and load one version's game data into the database; `output_count` reads either client's SpellEffect encoding
- `src/altarmy_profit/engine.py` – pure profit/chain logic (no I/O). Every tree `Node` lists its `options` (vendor, ah, `craft:<recipe id>`, cheapest first) and the `option` taken; `Result.sell_options` gives each exit's best profit. `evaluate(recipe, choices)` takes user picks keyed by tree path (`r.0`, `r.0.1`; `sell` for the exit); subtrees with a pick skip the memo. With a `TimeModel(config, city)` (`Market(time=)`), nodes, options, steps and results carry seconds (all `compare=False`), options and exits are ranked by copper plus `time_value` x estimated seconds (`Market._effective`; a time value of 0 changes no plan), and `Result.timing` (lazy, like `steps`: `rank()` never times) routes the plan through the city (`time_result`); `Result.rate` is copper per hour
- `src/altarmy_profit/prices.py` – the price store and its sources: auction houses (`find_auction_house`, `auctionator_auction_house`, `unnamed_auction_house`), `record_snapshot` (the one way prices get in; writes observations only for news and moves `price_current`), `record_daily` (pools uploaders' days: min low, max high, max available), `prune`, `load_current`, `load_buy_and_sell` (the engine's buy and sell prices), `auction_houses` (with price counts), `coverage`, `stats`, `daily`; `screen`/`baseline` (quarantine), `record_auctionator(..., trust=)` returns `Recorded`; CSV, manual and Auctionator imports
- `src/altarmy_profit/merge.py` – the merge (`altarmy-profit merge`, hourly Cloud Run job; local sync runs it per auction house): `price_daily.median` and `price_current`'s 7-day columns, bumping `auction_houses.price_version` when anything moved
- `src/altarmy_profit/auctionator.py` – pure parser for Auctionator's SavedVariables (Lua string holding CBOR): per item an `ItemPrice` (latest minimum buyout, per-day `DayStats` high/low/available)
- `src/altarmy_profit/timing.py` – pure play-time model (no engine import; the engine imports it): `TimeConfig` (seconds per action, `batch` crafts per session, `time_value` copper per hour of play, run speed, detour; `config_from_dict` strict, `config_from_json` lenient, `config_changes` what is stored), `CityMap` (locations in yards, vendors' stock, hub, `overrides`; `from_dict`, `seconds`, `nearest`, `vendor_for`, `trip`; memoized, shared across threads), `ANYWHERE` (the one-spot city when a version has no presets), `station_kind` (a SpellFocusObject name as a location kind), `Block`/`route`/`time_blocks` -> `Timing` (fixed and per-craft seconds, `breakdown`, `legs`, `unsold`, `missing`, `per_hour`)
- `src/altarmy_profit/cities.py` – pure builder of city presets (`CITY_SPECS`, `build_city`) from vmangos spawns (`vmangos.city_centre`, `npcs_near`, `objects_near`, `vendor_stock`); `scripts/build_cities.py` writes `data/forever/cities/*.json`, keeping each preset's hand-tuned `overrides`
- `src/altarmy_profit/talents.py` – the Legacy talents (WoW: Forever) that change profits, by spell id (`LEGACY_TALENTS`: Master Chef, Bartering); `extra_results`/`vendor_discount` turn a character's (spell id, rank) pairs into `engine.Crafter` fields, `known` lists them for the API
- `src/altarmy_profit/luasv.py` – pure generic parser for SavedVariables files (`Name = <Lua table>` statements); nesting capped at `MAX_DEPTH`
- `src/altarmy_profit/altarmy.py` – pure reader for the Alt Army addon's `AltArmy_TBC.lua`: characters, professions, learned recipe ids (= `recipes.spell_id`); `groups` by realm/faction, `crafters`; `CLASS_FILES` and `max_rank_for` for hand-made characters
- `src/altarmy_profit/store.py` – `load_market(conn, game_version, auction_house_id, ah_cut=, mail_postage=)`: database rows to engine dataclasses; characters (`save_characters` replaces all, `upsert_character`/`delete_character` one) and AH blocks per user and version; `profession_names` (without `HIDDEN_PROFESSIONS`: class skills and a test line DB2 gives recipes)
- `src/altarmy_profit/ratelimit.py` – pure in-memory sliding-window `RateLimiter` (per instance), `Limits`/`HOSTED_LIMITS` (per IP 300/min, per uid 120/min), `client_ip` (first `X-Forwarded-For` entry: right through Firebase Hosting, spoofable on the direct run.app URL)
- `src/altarmy_profit/service.py` – web use-cases (every per-user function takes `user_uid` after `conn`): `MarketCache` (per version, one `Market` per auction house; rebuilt after `invalidate()` or when `store.market_stamp` (build, newest snapshot id, `price_version`) moved, checked at most every `STAMP_TTL` s, so other instances' uploads, the ingest job and the merge show up); `RankCache` (the last 64 full rankings, valid only for the very `Market` they were ranked on; `/api/rank` slices `top` from it, so paging doesn't re-rank); `search` over the selected realm/faction's characters (`engine.recipes_for_characters`: learned recipes, or with `include_unlearned` every recipe of their professions; chains only sub-craft through those; without characters every recipe, for one unnamed crafter), selling only via the allowed exits and keeping what an `engine.Filters` (min/max cost, profit, ROI) accepts; `evaluate`: one recipe with the user's `choices`; `imply_recipes` (a hand-made character, with professions but no learned recipe, knows every recipe of its professions); realm/faction `selection` (saved if it has characters or an auction house, else the biggest group, else `prices.freshest_auction_house`) and its auction house (`selected_auction_house`, `pricing_auction_house`); `select` takes a group or any named auction house; `replace_characters` (imports: forgets a selection the new characters aren't on), `create_character` (hand-made, `MAX_CHARACTERS`), `delete_character`; `sync` (local mode only), which re-imports Alt Army characters and records the selected realm's Auctionator scan (every realm while there are no characters) whenever either file's mtime changes; game data update
- `src/altarmy_profit/api.py` – FastAPI JSON API (`create_app(game_versions, database=..., mode=, verifier=, firebase=)`: one shared `Database`, a market cache and locks per version; tests pass `mode` and a fake `verifier`); also serves the built `frontend/dist`. Dependencies: `CurrentUser` (local: `LOCAL_USER`; hosted: the bearer Firebase ID token, 401 without), `LinkedUser` (403 for free: only the API key routes; guests get everything else, and there is no level gate for now), `LOCAL_ONLY` (404 in hosted: sync, sources, file lookups, game-data update, reload), `HOSTED_ONLY` (404 in local: `DELETE /api/me`, which deletes the user's rows and, in the same transaction, the Firebase user). Hosted mode rate-limits per client IP (middleware) and per uid (in `CurrentUser`/`Uploader`), 429 with `Retry-After`; every /api response carries `Cache-Control: no-store` (Hosting's CDN). `create_app` in hosted mode builds its default `Database` with `migrate=False`. `Uploader` (upload route only: a Firebase token or an `ak_` API key; local mode ignores both). Public: `/api/config` (mode, Firebase web config), `/api/versions`. `POST /api/uploads` (multipart `file`, `kind`, `modified_at` ms, `via`; plain or gzipped; 400 bad file, 413, 429; every outcome in `uploads`), `POST /api/uploads/paste` (JSON `text`: the addon's export; recorded as kind `altarmy`, via `paste`; 400 for another game's export), `GET /api/uploads`; `/api/keys` GET/POST and `DELETE /api/keys/{id}` (LinkedUser). `/api/me`; `/api/coverage` (each realm's last scan, stalest first on the Upload page). `ItemInfo` carries `ah_price` (buy) and `ah_sell_price` (what the AH exit counts). Every per-game route takes a required `game_version` query parameter (the `State` dependency); `GET /api/versions` lists them. The front end serves Forever only: `lib/gameVersion.ts`'s `GAME_VERSION` constant is sent with every request and put first in every query key after the route name. `GET /api/status` runs the addon sync in local mode only, and the front end polls it (every 30 s and on window focus); its `data_version` and `price_version` (the selected auction house's) together are `useDataVersion()`, part of the characters/rank/evaluate/prices query keys. `POST /api/evaluate` re-costs one recipe with the choices the user made in its flow chart or step list (both use `components/ChoiceMenu.tsx`; each step's `paths` name the tree nodes it stands for, several when merged, and `lib/steps.ts` maps them back; `ResultsTable` holds the choices per recipe, `lib/choices.ts`; the row then shows the changed plan until Reset). `GET /api/rank` takes `exits`, optional bounds (omitted = unbounded) and `professions` (the bounds and the profession filter narrow the cached, unbounded ranking, so they are not in the rank cache key; browsing without characters shares one cache entry across users) and returns the first `top` results plus `total`; the search pages through them 50 at a time. `GET /api/professions`; `POST /api/characters` (a hand-made `ManualCharacter`, validated against the version's classes, caps and professions) and `DELETE /api/characters?realm=&name=`. The built front end is served by `_SpaFiles`: `index.html` for the app's own paths (`/addon`, `/manage`, ...)

## Commands

Use the project venv (`.venv`); do not install packages globally. If it is missing: `python -m venv .venv`, then `.venv\Scripts\python -m pip install -e ".[dev,ui]"` (add `,tray,build-tray` for the tray app). Front-end packages live in `frontend/node_modules` (`npm ci` in `frontend/`); the root `package.json` only holds dev tooling (`npm ci` in the root).

- `python scripts/check.py` – ruff lint, ruff format check, mypy (strict), pytest, then regenerates the OpenAPI spec and TS types and runs oxlint, vitest and `tsc -b && vite build`. **Run before considering any change done.** Pass `--skip-frontend` for Python-only iteration.
- `ruff check . --fix`, `ruff format .`, `mypy`, `pytest` – individual Python tools; `npm run lint|test|build|dev|gen-types` in `frontend/`.
- Postgres: set `TEST_DATABASE_URL` (e.g. `postgresql+psycopg://postgres:postgres@localhost:5432/altarmy_test`) and run `pytest`; the tests drop and recreate that database's `public` schema, so never point it at real data. CI does this on every push.
- Schema changes: edit `schema.py`, then `alembic revision --autogenerate -m "..."` (uses `DATABASE_URL`, else `data/altarmy-profit.sqlite`; point it at a database migrated to head), review the revision (SQLite needs batch operations; `env.py` renders them) and keep `test_migrations.py` green on both databases.
- Deploy: see README's "Deploy" (Git Bash). Creating, changing or deleting cloud resources is visible and billed: show the command and get the user's OK first; read-only gcloud is fine.
- Dev loop: `npm run dev` in the repo root runs the API (`scripts/dev-api.mjs`, venv python, :8600) and, once it answers, Vite on :5173, which proxies `/api` to it.

## Conventions

- **Money is integer copper** everywhere (prices, costs, profit), including the JSON API. Format only at the display edge: `format_money` in Python (CLI), the `Money` component (`frontend/src/components/Money.tsx`, coin icons) in the front end.
- **User state is per user**: characters, `user_settings`, `local_sync` and `ah_blocked` carry `user_uid`; store/service/users functions take it right after `conn`. The CLI, `legacy.py` and scripts act as `db.LOCAL_UID`. Never gate on mode inside service code: tiers and modes are the API's dependencies.
- **Uploads are untrusted**: on bad input the parsers must only raise `ValueError` (the API's 400); `test_mangled_files_only_raise_value_error` fuzzes them. Never store an uploaded file.
- **Migrations run once per deploy** (`altarmy-profit migrate` as a Cloud Run job, before the service); hosted instances never migrate. Keep revisions safe for the previous release's instances still serving (additive first).
- API handlers are plain `def` (FastAPI runs them in a threadpool) and open their own connection per request (`database.begin()`); never share a connection across threads.
- **Storage is SQLAlchemy Core** (no ORM) against `schema.py`, and must work on SQLite and Postgres: no raw SQLite-only SQL (`INSERT OR REPLACE`, `PRAGMA`) outside `db.py`'s engine setup and `legacy.py`; use `db.upsert`. Functions taking a `Connection` never commit: the caller owns the transaction (`Database.begin()` in the API and CLI; tests use an autocommit connection). Order query results explicitly; row order is not insertion order on Postgres.
- After changing API models or routes, regenerate `frontend/openapi.json` and `frontend/src/api/schema.d.ts` (`check.py` does this) and commit both.
- **Keep `engine.py` pure**: no file, DB or network access. Load data in `store.py` and pass plain dataclasses in.
- **Type annotations are required**; mypy runs in strict mode over `src` and `tests`, and the front end uses TypeScript `strict`.
- Prefer red-green-refactor: write a failing test first, then make it pass. Ingest tests use fixture CSVs, never the network. API tests use FastAPI's `TestClient`; front-end tests use vitest + Testing Library with `fetch` stubbed (`frontend/src/test/utils.tsx`).
- Line length is 110; let `ruff format` handle style.

## Data gotchas

- Local mode keeps **one SQLite file** (`data/altarmy-profit.sqlite`) for both versions, the same schema as Postgres. Game data is keyed by `game_version`; `user_settings` (selection, `data_version`), `local_sync` (addon paths, mtimes), characters and `ah_blocked` by `user_uid` and `game_version`; item and recipe ids are only meaningful within one version. The pinned/loaded build is `game_versions.build`. `recipe_reagents.slot` keeps DB2's reagent order, which the flow chart's choice paths (`r.0`, `r.1`) depend on.
- Disenchant results are server-side loot data and are **not** in DB2. Without a version's `disenchant.csv`, disenchant is ignored. Do not invent drop tables.
- DB2 does not say which vendors sell which items. `data/<version>/vendor_items.csv` (unlimited stock, no condition, no token cost, spawned vendor) says which; the per-unit price is `items.buy_price / items.buy_count` (DB2 `BuyPrice` / `VendorStackCount`), rounded up. The engine buys each reagent from the cheaper of vendor and AH (ties go to the vendor). DB2's `BuyPrice` is set on nearly every item, so it alone does not mean a vendor sells it.
- `recipes.min_skill` currently comes out as 1 for every real recipe, so do not rely on it. Recipe output count comes from `SpellEffect.EffectBasePointsF` and is only spot-checked. `recipes.cast_time_ms` (SpellMisc -> SpellCastTimes, the DifficultyID 0 row) and `recipes.station` (SpellCastingRequirements' SpellFocusObject name as `timing.station_kind` spells it: anvil, cooking_fire, loom, ...) read 0 and "" in older databases until the next game data update. WoW: Forever adds stations vanilla never had (spinning wheel, sewing machine, tanning rack, loom, master forge, iron oven, alchemy lab, ...): vmangos has no positions for them. Until we learn how they work they are `timing.DEPLOYABLE`: set down where the crafter stands, so never a trip and never `missing`; `Timing.deployed` lists them and the UI names them.
- **Profit per hour.** Seconds are per craft of the evaluated recipe: a batch clicks once per whole stack and sends whole mails (`Market._stacks`: one salt a craft is one stack-click per batch of 20), and those clicks, trips from the hub, AH searches and character switches are divided by `TimeConfig.batch`. The per-user time settings are `user_settings.time_city`/`time_config` (JSON of the changes from the defaults), read by `service.time_model` (the saved city if the selection's faction crafts there, else `service.default_city`: Orgrimmar/Stormwind, else the faction's first, else `timing.ANYWHERE`). `/api/rank`'s cache key includes `TimeModel.key`; `sort=rate` sorts the cached ranking (`service.by_rate`, cached as its own entry), timing every result once. `RankResult.cities` times the chosen plan in each of the faction's cities (never neutral towns: Booty Bay's, Gadgetzan's and Everlook's auction house is not the one prices track, so there are no presets for them); `best_city` is the quickest without `missing` stations. Presets load lazily per version (`AppState.cities`; local `/api/reload` forgets them).
- Item tooltips (`store.load_item_details`, `/api/rank`'s `items` map) use denormalized `items` columns filled at ingest: subclass names from `ItemSubClass`, icon names from `ManifestInterfaceData` (`Interface\Icons` only; the browser loads them from wow.zamimg.com). Stats, armor and weapon damage are not shown: ItemSparse holds only stat allocations. `db.init_schema` adds missing item columns to older databases; they stay empty until the next game data update.
- Re-running `altarmy-profit ingest` rebuilds that version's items, recipes and disenchant rows but leaves prices, users and their characters, settings, `ah_blocked` and the other version alone.
- **Prices are per auction house** (`auction_houses`: version, realm, faction; faction `""` = one shared by both factions, as Forever's `ClassicBetaPvE`; realm `""` = the unnamed one CLI prices use before any characters exist). A selection's auction house is its faction's, else its realm's shared one (`prices.find_auction_house`); an Auctionator key ending in the faction means a split house. Every source records a `price_snapshots` row; `price_observations` get only news (no current price, a later day, or a different price seen no earlier) and move `price_current`, which the engine reads; the newest `seen_at` wins whatever the source, so a manual price holds until a later scan. An Auctionator item was seen at the scan time if its last day is the scan day, else at the start of that day. `price_daily` comes from Auctionator's h/l/a (high = highest minimum buyout that day, low = `l` or else `h`, available = most seen) and is only rewritten from the newest stored day on, pooling uploaders (min low, max high, max available). Observations older than 90 days are pruned at each sync; snapshots `price_current` points at are kept. Money columns for prices are `BigInteger` (copper exceeds 2^31).
- **Buy vs sell price.** `Market.prices` (buying reagents) is `price_current.price`; `Market.sell_prices` (the AH exit, disenchant materials) is the lower of it and `median_7d`, except for `manual`/`csv` snapshots. `median_7d` is the median of the item's daily medians over its latest 7 days with data within 30 days (not 7 calendar days: one player's sparse scans would leave a lone spike as the only sample); `scans_7d` counts those days. `price_daily.median` = median of the day's low, high and that UTC day's accepted scan prices (clamped). The merge fills them; until then the sell price is the price.
- **Quarantine.** Only uploads are screened (local sync and CLI imports are not; `trust=None`). A scan is quarantined when at least 20 of its fresh prices can be compared with a baseline (`median_7d` with `scans_7d >= 3`) and more than `0.1 + 0.2 * trust` of them are over 4x off either way (real TBC scans: at most ~5%). A quarantined snapshot is a `status='quarantined'` row only: no observations, no `price_current` or `price_daily` change; the merge ignores it.
- `ah_blocked` holds items the user never wants sold on the AH (per game version, not per realm; set from a search row's ⋯ menu, listed on the Manage page, `/api/ah-blocked`). It is passed per request as `Market(no_ah=...)`, which drops only the `ah` exit for those items: they can still be bought on the AH, and disenchant materials are still valued at AH prices. The cached base market never holds it, so toggling needs no cache invalidation.
- Alt Army recipe ids are craft spell ids. On TBC clients one recipe is stored under several alias keys sharing a `primaryRecipeID`; Enchanting rows carry only `color`. Auctionator keys realms as the realm name without spaces, plus the faction where auction houses are split (`ClassicBetaPvE`, `Dreamscythe Horde`); `service.match_auctionator_realm` maps a realm/faction to it, and the key is stored as a `realm_aliases` row. Auctionator's day numbers count from 2020-01-01 in local time; it drops days older than its history setting, and random-suffix gear (`gr:` keys) is skipped.
- Characters and mail: `Market` gets the selected characters as `engine.Crafter`s and costs every craft *at a character* (`Market._obtain`): each reagent is bought there, or crafted by any character who can (learners, or with `include_unlearned` and no learner, anyone with the profession) and mailed over if that is someone else. The final crafter is whichever gives the best profit. Postage is `MAIL_POSTAGE` (30c) per attachment, one stack each (`items.stack_size` from `ItemSparse.Stackable`; older databases read 1 until the next game data update). A disenchant is free if the final crafter enchants, else the output is mailed to the best enchanter; with no enchanter at all the disenchant exit is dropped. Postage is in `cost` and shown as `mail` steps and flow nodes; steps carry `who`. `engine.plan_steps` (a `Result`'s `steps`, planned when first read, so a ranking never schedules results nobody looks at) orders them dependencies first and then per character (`engine._schedule`): each does all their buys, then crafts, then mails before another takes over, whoever can finish outright first, so a character is revisited only for what waited on someone's mail. Without crafters (CLI `rank`, or browsing without characters on the web) one unnamed character does everything, so nothing is mailed; the results table shows "anyone" as the crafter. Hand-made characters (`POST /api/characters`) know no recipe ids; `service.imply_recipes` gives them every recipe of their professions before ranking. Costs are whole batches (spares from multi-output crafts are not credited). Soulbound items (`Item.tradable` False: `items.bonding` 1 or 4) are never mailed, so only the character who needs such an intermediate crafts it, a soulbound craft is disenchanted only by its crafter, and it gets no AH exit. One `Memo` serves a whole `rank()` (keyed on item, quantity, character and depth, not the ancestors): chains stop at `MAX_CHAIN_DEPTH`, which also ends cycles, and a recipe consuming its own output is skipped.
- Legacy talents (WoW: Forever): the addon saves `legacyTalents.spells[spellID] = rank` (data version 2; v1 data without `spells` was the class-talent config and is ignored) and exports `T|` lines. They are stored in `character_talents`, kept on `Character.talents`, and mapped by `talents.py`:
  - **Bartering** (1225459, 5% per rank, 2 ranks) makes that character's own vendor buys cheaper: the unit price is rounded up, and the discount is on `Node.discount` and `Step.discount`. Nobody buys on a barterer and mails the goods on.
  - **Master Chef** (1225457, 10% per rank, 5 ranks) gives the final Cooking craft `output_count + chance` expected units in its revenue, reported as `Result.bonus_output` and the sell `Step.bonus`. Sub-crafts get no bonus, and postage on the extras is not charged.
  - Hand-made characters have no talents.
  - The DB2 source is `TraitSystem` 45 with trees 1187-1189 (see the addon's research doc).
- The pinned builds are `GameVersion.default_build` in `versions.py`; `ingest.latest_build(product)` resolves the newest build of a wago.tools product (`wow_classic_beta`, `wow_anniversary`) from its `/api/builds/latest` JSON. TBC's SpellEffect leaves `EffectBasePointsF` at 0 and encodes counts as `EffectBasePoints` + a 1..`EffectDieSides` roll. Downloaded CSVs are cached under `cache/` (git-ignored, as is `data/*.db`).
